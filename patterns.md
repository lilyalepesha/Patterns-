# Singleton (Одиночка)

> **Категория:** порождающий паттерн (Creational Pattern).  
> **Назначение:** контролировать создание экземпляров класса и предоставлять доступ к одному общему экземпляру.

## 1. Суть паттерна

**Singleton гарантирует существование одного экземпляра класса в определённом контексте и предоставляет единую точку доступа к нему.**

Предположим, в приложении есть три компонента:

- `UserService` — работает с пользователями.
- `PaymentService` — обрабатывает платежи.
- `OrderService` — работает с заказами.

Каждый компонент может создать собственный объект логгера:

```php
$userLogger = new Logger();
$paymentLogger = new Logger();
$orderLogger = new Logger();
```

В результате существуют три независимых экземпляра.

Singleton позволяет получать один и тот же объект:

```php
$userLogger = Logger::getInstance();
$paymentLogger = Logger::getInstance();
$orderLogger = Logger::getInstance();
```

Теперь все три переменные ссылаются на один экземпляр.

> **Важно:** Singleton не обеспечивает единственный объект на всём сервере. В PHP экземпляры существуют в контексте выполнения и соответствующего процесса.

## 2. Какую проблему решает

Паттерн централизует создание объекта, когда приложение должно повторно использовать один экземпляр определённого класса.

Основная идея:

1. Запретить создание объектов извне.
2. Хранить созданный экземпляр в статическом свойстве.
3. Предоставить метод для получения экземпляра.
4. При первом обращении создавать объект, а при последующих возвращать существующий.

Таким образом, ответственность за создание экземпляра сосредоточена внутри класса.

## 3. Реализация на PHP

Рассмотрим классический Singleton на примере логгера.

```php
<?php

declare(strict_types=1);

final class Logger
{
    private static ?Logger $instance = null;

    private function __construct()
    {
    }

    private function __clone()
    {
    }

    public function __wakeup(): never
    {
        throw new LogicException(
            'Cannot unserialize a singleton.'
        );
    }

    public static function getInstance(): Logger
    {
        return self::$instance ??= new self();
    }

    public function log(string $message): void
    {
        $date = date('Y-m-d H:i:s');

        file_put_contents(
            __DIR__ . '/app.log',
            "[$date] $message" . PHP_EOL,
            FILE_APPEND | LOCK_EX
        );
    }
}
```

### Основные элементы реализации

| Элемент | Назначение |
|---|---|
| `private static ?Logger $instance` | Хранит ссылку на созданный экземпляр или `null`, если его ещё нет. |
| `private function __construct()` | Запрещает создавать объекты через `new Logger()` извне. |
| `private function __clone()` | Запрещает клонирование объекта извне. |
| `__wakeup(): never` | Запрещает успешную десериализацию объекта. |
| `getInstance()` | Создаёт экземпляр при первом обращении и возвращает его при последующих. |
| `final class Logger` | Запрещает наследование класса. |

## 4. Разбор реализации

### 4.1. Статическое свойство

```php
private static ?Logger $instance = null;
```

Статическое свойство принадлежит классу, а не отдельному объекту.

Тип `?Logger` допускает два состояния:

- `null` — экземпляр ещё не создан;
- `Logger` — экземпляр уже существует.

Благодаря этому класс может хранить ссылку на созданный объект.

### 4.2. Приватный конструктор

```php
private function __construct()
{
}
```

В обычном классе можно написать:

```php
$logger = new Logger();
```

Но приватный конструктор запрещает создавать объект таким способом извне.

Создание объекта остаётся доступным внутри самого класса:

```php
new self();
```

Это позволяет контролировать процесс создания экземпляра.

### 4.3. Метод getInstance()

```php
public static function getInstance(): Logger
{
    return self::$instance ??= new self();
}
```

Оператор `??=` присваивает значение только в том случае, если левая часть равна `null`.

Логика эквивалентна следующему коду:

```php
public static function getInstance(): Logger
{
    if (self::$instance === null) {
        self::$instance = new self();
    }

    return self::$instance;
}
```

**Первый вызов:**

1. `$instance` равен `null`.
2. Создаётся новый объект.
3. Ссылка сохраняется в `$instance`.
4. Объект возвращается вызывающему коду.

**Последующие вызовы:**

1. `$instance` уже содержит объект.
2. Новый объект не создаётся.
3. Возвращается сохранённый экземпляр.

### 4.4. Запрет клонирования

```php
private function __clone()
{
}
```

Без этого ограничения можно было бы создать копию:

```php
$logger = Logger::getInstance();

$anotherLogger = clone $logger;
```

Клонирование создало бы другой объект.

Приватный `__clone()` запрещает такую операцию извне.

### 4.5. Запрет десериализации

```php
public function __wakeup(): never
{
    throw new LogicException(
        'Cannot unserialize a singleton.'
    );
}
```

При десериализации PHP восстанавливает объект из сериализованных данных и вызывает `__wakeup()`, если этот метод определён.

В данном случае метод выбрасывает исключение.

Тип `never` означает, что метод не завершается обычным образом: он всегда прерывает выполнение, выбрасывая исключение.

### 4.6. Почему класс final?

```php
final class Logger
```

`final` запрещает наследование класса.

Это упрощает соблюдение ограничений Singleton и исключает создание подклассов с потенциально отличающимся поведением.

---

## 5. Проверка работы

Получим экземпляр дважды:

```php
$first = Logger::getInstance();
$second = Logger::getInstance();

var_dump($first === $second);
```

Результат:

```text
bool(true)
```

Обе переменные ссылаются на один и тот же объект.

Теперь используем логгер:

```php
$first->log('User registered');
$second->log('Payment completed');
```

В файл `app.log` будут добавлены обе записи.

### Ограничения

Singleton гарантирует повторное использование экземпляра только в пределах соответствующего состояния класса и процесса выполнения.

Например, разные PHP-FPM-воркеры могут иметь собственные экземпляры `Logger`. Для общего состояния между процессами нужны отдельные механизмы хранения.

## 6. Реализация в Laravel

В Laravel обычно не требуется реализовывать классический Singleton вручную.

Вместо этого можно поручить управление жизненным циклом объекта **Service Container**.

### 6.1. Создание обычного сервиса

Файл `app/Services/Logger.php`:

```php
<?php

declare(strict_types=1);

namespace App\Services;

class Logger
{
    public function log(string $message): void
    {
        logger()->info($message);
    }
}
```

Это обычный класс без статического свойства, приватного конструктора и метода `getInstance()`.

### 6.2. Регистрация Singleton

В `app/Providers/AppServiceProvider.php`:

```php
<?php

namespace App\Providers;

use App\Services\Logger;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->singleton(Logger::class);
    }
}
```

Если провайдер уже содержит другие регистрации, достаточно добавить строку в существующий метод `register()`.

```php
$this->app->singleton(Logger::class);
```

Теперь контейнер Laravel:

1. Создаёт экземпляр при первом разрешении зависимости.
2. Сохраняет созданный объект.
3. Возвращает сохранённый экземпляр при последующих разрешениях в рамках жизненного цикла контейнера.

### 6.3. Использование через Dependency Injection

```php
<?php

namespace App\Http\Controllers;

use App\Services\Logger;

class UserController extends Controller
{
    public function __construct(
        private Logger $logger
    ) {
    }

    public function index()
    {
        $this->logger->log('User list requested');

        return response()->json([
            'message' => 'Users retrieved',
        ]);
    }
}
```

Laravel автоматически разрешает зависимость `Logger` и передаёт объект в конструктор контроллера.

Не нужно вручную создавать объект:

```php
$this->logger = new Logger();
```

Не требуется и статический вызов:

```php
Logger::getInstance();
```

**Главное отличие:** в классическом Singleton класс сам контролирует создание экземпляра, а в Laravel эту ответственность можно передать контейнеру зависимостей.

> **Важно:** обычный PHP-FPM, как правило, создаёт контейнер приложения для обработки запроса. В долгоживущих процессах, например Laravel Octane, необходимо дополнительно учитывать жизненный цикл объектов и риск сохранения изменяемого состояния между запросами.

## 7. bind() vs singleton() vs instance()

В Laravel существуют три способа регистрации зависимостей, которые важно различать.

| Метод | Поведение |
|---|---|
| `bind()` | Обычно создаёт новый экземпляр при каждом разрешении зависимости. |
| `singleton()` | Повторно использует экземпляр, созданный при первом разрешении. |
| `instance()` | Регистрирует уже созданный объект в контейнере. |

### bind()

```php
$this->app->bind(Logger::class);
```

Проверка:

```php
$first = app(Logger::class);
$second = app(Logger::class);

var_dump($first === $second); // false
```

### singleton()

```php
$this->app->singleton(Logger::class);
```

Проверка:

```php
$first = app(Logger::class);
$second = app(Logger::class);

var_dump($first === $second); // true
```

### instance()

```php
$logger = new Logger();

$this->app->instance(Logger::class, $logger);
```

Контейнер использует уже созданный объект.

## 8. Преимущества и недостатки

### Преимущества

- Централизованное управление созданием экземпляра.
- Повторное использование одного объекта.
- Контроль над созданием экземпляров.
- Удобен в ситуациях, когда действительно требуется единственный экземпляр в пределах определённого контекста.

### Недостатки

- Глобальная точка доступа создаёт скрытую зависимость.
- Статическое состояние затрудняет изолированное тестирование.
- Класс становится ответственным за собственное создание и управление экземпляром.
- Один экземпляр не означает один объект на весь сервер или между всеми процессами PHP.

---

## 9. Когда применять

Singleton стоит рассматривать, когда действительно необходимо централизовать создание единственного экземпляра.

При этом сам факт использования одного класса несколькими компонентами не означает, что ему обязательно нужен Singleton.

В Laravel чаще предпочтительнее:

- внедрять зависимости через конструктор;
- использовать Service Container;
- регистрировать `singleton()` только при необходимости повторного использования экземпляра;
- избегать глобального изменяемого состояния.

Например, для стандартного логирования обычно достаточно встроенного механизма Laravel:

```php
use Illuminate\Support\Facades\Log;

Log::info('Car synchronization started');

Log::error('Car synchronization failed', [
    'car_id' => 123,
]);
```

---

## 10. Что запомнить

1. Singleton — порождающий паттерн проектирования.
2. Он контролирует создание экземпляров и предоставляет доступ к одному объекту в определённом контексте.
3. Классическая реализация использует приватный конструктор, статическое свойство и `getInstance()`.
4. `__clone()` может запрещать клонирование, а `__wakeup()` — десериализацию.
5. В Laravel аналогичное управление жизненным циклом объекта обычно реализуется через `$this->app->singleton()`.
6. `bind()` и `singleton()` различаются политикой повторного использования экземпляров.
7. Singleton не гарантирует общий экземпляр между независимыми PHP-процессами.
8. Не следует применять Singleton без конкретной необходимости: в Laravel обычно предпочтительнее Dependency Injection.

**Ключевая идея:** Singleton — не просто способ получить один объект, а решение, которое ограничивает создание экземпляров и вводит определённую модель управления их жизненным циклом.

# Static Factory (статическая фабрика)

## 1. Что это такое

**Static Factory** — это подход, при котором объект создаётся через статический метод, а не напрямую через `new` в вызывающем коде.

Вместо:

```php
$money = new Money(1500);
```

можно написать:

```php
$money = Money::fromCents(1500);
```

Метод `fromCents()` создаёт объект и возвращает его.

Static Factory — это не один из пяти классических порождающих паттернов GoF, а распространённый приём проектирования, который часто используют вместе с другими паттернами.

## 2. Зачем мне использовать Static Factory

Главная задача — **перенести правила создания объекта внутрь самого класса и дать созданию понятное имя**.

Представим, что в приложении есть денежная сумма. Она хранится в целых числах — в минимальных единицах валюты, например в копейках.

```php
$price = new Money(1500);
```

Что означает `1500`? Это 1500 рублей, 15 рублей или 1500 копеек? По самому вызову неясно.

Теперь посмотрим на другой вариант:

```php
$price = Money::fromCents(1500);
```

Название метода сразу объясняет, в каких единицах передаются данные.

Но это только одно преимущество. Static Factory полезен и в других ситуациях:

- **Скрывает детали создания.** Вызывающему коду не нужно знать, как именно подготавливается объект.
- **Позволяет проверять входные данные.** Некорректный объект можно не создавать.
- **Даёт несколько понятных способов создания.** Например, из копеек, из строки или как нулевую сумму.
- **Централизует правила создания.** Вместо повторения проверок в контроллерах и сервисах правила находятся в одном месте.
- **Делает код понятнее.** `User::fromEmail($email)` выразительнее, чем безымянный `new User(...)` с набором аргументов.

Важно: Static Factory не делает автоматически любой класс лучше. Если создание объекта простое и никаких дополнительных правил нет, обычный `new` вполне подходит.

## 3. Практический пример: класс Money

Создадим класс, который представляет денежную сумму в минимальных единицах валюты.

```php
<?php

declare(strict_types=1);

namespace App\ValueObjects;

use InvalidArgumentException;

final class Money
{
    private function __construct(
        private readonly int $cents,
    ) {
    }

    public static function fromCents(int $cents): self
    {
        if ($cents < 0) {
            throw new InvalidArgumentException(
                'Money cannot be negative.'
            );
        }

        return new self($cents);
    }

    public static function zero(): self
    {
        return new self(0);
    }

    public function cents(): int
    {
        return $this->cents;
    }
}
```

Использование:

```php
$price = Money::fromCents(2500);
$emptyBalance = Money::zero();

echo $price->cents(); // 2500
echo $emptyBalance->cents(); // 0
```

### Что здесь важно

**1. Приватный конструктор**

```php
private function __construct(
    private readonly int $cents,
) {
}
```

Теперь внешний код не может написать:

```php
$money = new Money(-500);
```

Создание объекта должно проходить через предусмотренные методы класса.

**2. Именованный способ создания**

```php
public static function fromCents(int $cents): self
```

Название `fromCents()` объясняет, что передаётся методу.

**3. Проверка данных в одном месте**

```php
if ($cents < 0) {
    throw new InvalidArgumentException(
        'Money cannot be negative.'
    );
}
```

Все места в приложении, создающие `Money` через `fromCents()`, получают одинаковую проверку.

**4. Специальный способ создания**

```php
public static function zero(): self
{
    return new self(0);
}
```

Если часто требуется нулевая сумма, не нужно каждый раз писать `Money::fromCents(0)`. Метод `zero()` явно выражает намерение.

**5. Возврат `self`**

```php
public static function fromCents(int $cents): self
```

`self` означает, что метод возвращает экземпляр этого класса.

Внутри статического метода используется `new self(...)`, поскольку конструктор закрыт для внешнего кода.

## 4. Когда Static Factory действительно нужен

### Ситуация № 1. Объект имеет правила создания

Например, нельзя создать денежную сумму с отрицательным значением.

```php
$money = Money::fromCents(-100);
```

Метод проверит значение и выбросит исключение.

**Почему это полезно:** правила не размазываются по контроллерам, сервисам и другим местам приложения. Класс сам контролирует допустимое состояние создаваемых объектов.

### Ситуация № 2. Есть несколько способов создания одного объекта

Например, приложение получает стоимость в разных форматах:

```php
Money::fromCents(2500);
Money::zero();
```

В более сложном классе могли бы быть методы `fromString()`, `fromArray()` или `fromDatabase()` — если соответствующие форматы действительно нужны.

**Почему это полезно:** вызывающий код явно указывает источник или смысл данных, а не передаёт неочевидные аргументы в конструктор.

Не следует добавлять такие методы только ради их количества: каждый должен представлять реальный сценарий создания.

### Ситуация № 3. Конструктор снаружи использовать нежелательно

Если создание объекта должно всегда проходить через проверку или специальную подготовку, конструктор можно сделать `private`.

**Почему это полезно:** нельзя случайно обойти предусмотренный способ создания объекта.

Однако приватный конструктор ограничивает способы использования класса. Делать его приватным стоит только тогда, когда это соответствует задаче.

### Ситуация № 4. Нужно выразить смысл операции

Сравним:

```php
$user = new User($email, $password, true);
```

```php
$user = User::register($email, $password);
```

Второй вызов сообщает о намерении зарегистрировать пользователя.

Но здесь есть важная оговорка: если регистрация включает сохранение в БД, отправку письма, создание токена и другие побочные эффекты, это уже не просто создание объекта. Такую бизнес-операцию часто правильнее разместить в отдельном сервисе или Action, например `RegisterUserAction`, а не прятать всю логику внутри статической фабрики.

## 5. Применение в Laravel

Допустим, приложение получает стоимость объявления с AV.by и преобразует её в объект `Money`.

Это можно делать в сервисе синхронизации:

```php
$price = Money::fromCents($parsedPrice);
```

Сервису не нужно самостоятельно проверять, допустима ли сумма. Он использует единый способ создания объекта.

Упрощённый пример:

```php
final class ListingPriceMapper
{
    public function map(int $priceInCents): Money
    {
        return Money::fromCents($priceInCents);
    }
}
```

В этом примере `ListingPriceMapper` отвечает за преобразование данных, а `Money` — за допустимое состояние денежной суммы.

При этом Static Factory не заменяет Laravel Service Container. Для обычных сервисов, которым нужны зависимости вроде репозиториев, HTTP-клиентов или логгеров, обычно лучше использовать внедрение зависимостей через конструктор.

Например, такой сервис не стоит превращать в набор статических методов:

```php
final class ListingSyncService
{
    public function __construct(
        private readonly ListingRepository $listings,
        private readonly AvByClient $client,
    ) {
    }
}
```

Laravel сам создаст сервис и передаст ему зависимости.

## 6. Когда Static Factory не нужен

Не используйте этот подход автоматически для каждого класса.

Обычный конструктор подходит, когда:

- создание объекта простое;
- нет дополнительных проверок или правил;
- достаточно одного способа создания;
- нет необходимости ограничивать доступ к конструктору.

Например:

```php
final class Point
{
    public function __construct(
        public readonly int $x,
        public readonly int $y,
    ) {
    }
}

$point = new Point(10, 20);
```

Здесь `new Point(10, 20)` понятен, поэтому отдельная статическая фабрика может ничего не улучшить.

Также Static Factory сам по себе не решает задачу выбора между разными реализациями по конфигурации или типу входных данных. Для таких задач могут подойти отдельная фабрика, Factory Method или другой механизм.

## 7. Static Factory и Factory Method — в чём разница

| Static Factory | Factory Method |
|---|---|
| Обычно используется статический метод класса | Создание делегируется переопределяемому методу создателя |
| Удобен для именованных способов создания одного типа объекта | Удобен, когда подклассы должны выбирать создаваемую реализацию |
| Например, `Money::fromCents(2500)` | Например, разные создатели возвращают разные реализации `PaymentGateway` |

Не стоит путать название подхода со словом «фабрика» в общем смысле. Статический метод создания объекта не становится автоматически классическим паттерном Factory Method.

## 8. Главное, что нужно запомнить

Static Factory стоит использовать, когда **само создание объекта имеет смысл, который полезно явно выразить в коде**.

На практике это особенно полезно, если необходимо:

- централизовать проверки при создании объекта;
- предоставить несколько осмысленных способов создания;
- скрыть конструктор и контролировать допустимые состояния;
- сделать вызов более выразительным.

Если же объект создаётся элементарно и обычный конструктор всё объясняет, не нужно усложнять код.

**Правило:** сначала определите, какую проблему решает фабричный метод. Если он не делает создание понятнее, безопаснее или удобнее, оставьте `new`.
